# 逆向笔记

记录「为什么这么做」，免得下次重新踩。

## 车机助手

### 不能改它，只能挂上去

车机助手（`com.navi.tool`）是原厂桌面组件，改一个字节就等于换签名、覆盖安装失败、授权重来。
所以全部做法是：把我们的 dex 追加成 `classes3.dex`，靠三个系统入口把自己的代码跑起来。

| 入口 | 为什么选它 |
|---|---|
| `ContentProvider` | 进程一起来系统就调用 `onCreate`，比 Service 还早，最先拿到执行权 |
| 前台服务 `START_STICKY` | 进程被回收后自己回来；常驻通知让系统不轻易动它 |
| 开机广播 | `BOOT_COMPLETED` / `QUICKBOOT_POWERON`，车机一启动就顶服务 |

### 车控能力从哪来

`DesktopAssistantActivity` 里有一个 `carControlHelper` 对象，所有车控都是调它的方法。
`Bridge.install()` 通过反射抓这个实例：

- **只读引用，绝不新建**：构造第二个 Helper 会扰乱界面结构，界面会错乱
- Helper 只有 Activity 出现才有 —— 所以「桌面助手没跑」= 车控全废，`/diag` 里会写明绑没绑上
- `getCarInfoValue` 在测试机上返回空，因为没有车机总线，这是正常的，不是 bug

### 18766 为什么不能由桥接包提供

`carControlHelper` 是桌面助手 Activity 里的对象，**跨进程拿不到**。
桥接包（`com.luna.music.car`）在自己进程里再装一份 `Bridge` 也抓不到那个实例，只会空转。
所以 18766 必须在车机助手进程里 —— 这是「注入 dex」这套做法存在的唯一理由。

### 动作表怎么来的

反射枚举 `carControlHelper` 上存在的方法（`handle*` / `actionSet*`），能调通的才进动作表。
方法不存在的项标「已隐藏」，不返回给页面 —— 比「点了没反应」好排查。

`/act` 的参数就是方法名本身，不再走「id → 驼峰 → 猜方法名」那一层。

### 风量、温度、座椅为什么要单独开接口

| 项 | 为什么 | 做法 |
|---|---|---|
| 风量 | 原界面是滑条，**方法名筛不出来** | 单独走 `/fan`，命令号和档位范围照抄原界面：前排 1-7、后排 0-4（0 关） |
| 温度 | 同上，且只有整度 | `/temp`，15-30 ℃，没有滑条 |
| 座椅 | 只有「关 / 3 档」两态，`data = 目标档位 + 1` | `/seat`，回读只用于点亮和提示 |

后排通风直接删掉：这台车既没有命令号也没有状态位，留着只会让人以为能用。

### 网关为什么只透传字节

18766 要同时服务车控（纯 HTTP）、音乐（HTTP + WebSocket）、记录仪（HTTP）。
在中间解析 WS 帧意味着要自己实现握手、掩码、分片、控制帧，还要跟着两端的实现走。
所以 `Gateway` 只做 `ServerSocket` 字节对流：判定目标端口，把原始请求头 + 后续字节转过去。

判定规则简单到不会错：

- 带 `Upgrade: websocket` → 音乐后端（车控没有 WS）
- `/music/*` → 音乐后端，去前缀
- `/api/*` → 音乐后端，原样
- `/dvr*` → 18767，原样
- 其余 → 本地

音乐后端用 TCP 探活选定，缓存 3 秒、优先 18765，命中后做一次轻量复查。

## 行车记录仪

记录仪是奇瑞/星途的 `com.exeed.dvr`，在车机内网。本模块只做一件事：
**把它那个老式文件系统网页翻成 JSON / 转发字节**，不碰私有协议。

### 发现

TCP `<ip>:7878` 能连上即命中（只判通不通，不发命令）。
先试固定 IP，否则并发扫**车机所有网卡**的网段（各 1~254，命中即止）。
记录仪必须与车机某网卡同段，否则用「指定 IP」。

### 列表

抓 `GET http://<ip>/SD0/NOR/M_video/` 的目录页，扫全页 `href`：

- 带视频扩展名的是文件、不带的是子文件夹
- 大小取链接旁的 `84M` / `30M`
- 时间从文件名 `20261117_131002` 抠，认不出再取页面上的日期
- 不依赖具体固件的 HTML 结构

### 抓页兜底

- 绝对地址链接（`http://192.168.196.16/SD0/...`）只取路径
- 页面没有 `href`、只有 JS/JSON 里的文件名时按扩展名认
- 服务器偷偷 gzip 或只吃 HTTP/1.0 也照收
- 失败把状态行（`HTTP/1.1 200 OK` / `401` / `ERR …`）一起回给页面

解析不出列表时，把 `/dvr/fs?p=<目录>` 用 iframe 显示 —— 那是记录仪自己的目录页原样转出来的，
链接已改写成本地地址，点文件夹继续浏览、点文件直接下载。

### 下载

`GET <目录>/<filename>` 从记录仪 80 口**流式**转发，Range 头透传、保留 `206 + Content-Range`，
不攒整包 —— 一个视频几百 M，攒完再发会 OOM。

### 为什么 18767 独立于音乐服务

`DvrSvc` 是独立前台服务，`App.onCreate` 里无条件拉起，跟音源模式、停服标记完全无关。
所以：音乐切官方/第三方、用户停不停音乐服务、18764 起没起，都不影响 18767。
反过来说，「记录仪和音乐打在一个包里」只是**打包**层面，运行时不耦合，没必要拆成两个 APK。

## 页面侧

### 外壳为什么只有一份源码

18766 / 18765 / 18764 是三个不同进程下发的 HTML。外壳（状态行 + 切换条 + 设置面板）如果各写一份，
三个端口会慢慢长歪。所以源码只有 `web/shell/` 一份，构建时由 `stitch.py` 拼进三个页面，
`--check` 只验标记在不在。

### 为什么要构建号

iframe 的 URL 一直是 `/?pane=music`、`/dvr?pane=dvr`。即使服务端发了 `Cache-Control: no-store`，
WebView 仍有概率复用旧文档，于是页面里跑的还是装新包之前的旧代码 —— 症状看起来像「连不上」。
拼接时按内容算一个号写进 URL，内容一变号就变，缓存必然失配。

### 音乐页为什么直连后端端口

音乐控制靠 WebSocket。经过 `/music` 反代实测会出现「无限读条 → 跳断开」，
而浏览器单开 18765 是好的。所以从 18766 进来时，外壳先问 `/gateway` 拿到真实端口，
再把音乐页按 `http://<IP>:<实际端口>/` 贴进来 —— 等于回到验证过的那条路，地址栏仍是 18766。
