# 遥控协议 v0.1（草案）

> 状态：草案，阶段 0 源码勘察确认后冻结为 v1。
> 机读定义：[`../proto/protocol.json`](../proto/protocol.json)　校验脚本：`python proto/test_protocol.py`
> 两端各自实现同一份协议，**不共用构建、不引共享模块**。

## 1. 传输层

| 项 | 取值 |
|---|---|
| 协议 | WebSocket（RFC 6455），仅文本帧，UTF-8 |
| 端口 | 默认 `18765`，集中配置（`RemoteConfig.PORT`），不散落硬编码 |
| 路径 | `ws://<car-ip>:18765/` 固定根路径 |
| 一条帧 = 一条消息 | 不做批量、不做分片续帧、单帧上限 8 KB |
| 保活 | 手机每 20 s 发 `ping`，车机回 `pong`；60 s 无任何帧视为死连接并断开 |
| 绑定 | 只监听局域网接口；不对公网做端口映射 |

TLS 第一版不做。**明文局域网传输可被同网段嗅探**，PIN/Token 都能被截获，因此本方案只适用于可信车内局域网，不能对外宣称是加密安全方案。

## 2. 信封

```json
{"v": 1, "type": "command", "id": "c-4821", "ts": 1730000000000, "data": { ... }}
```

| 字段 | 必填 | 说明 |
|---|---|---|
| `v` | 是 | 协议版本，当前 `1`。不认识就回 `auth_result/pair_result` 失败或 `1001` |
| `type` | 是 | 消息类型，见下表 |
| `id` | 视类型 | 请求 ID，请求/响应型必填，由**发起方**生成，响应原样回带 |
| `ts` | 否 | 发送方毫秒时间戳，仅用于日志与调试，不做逻辑判断 |
| `data` | 视类型 | 该类型的载荷；无载荷可省略 |

顶层用 `data` 包一层而不是把字段摊平，是为了两端解析器都只需要「先看 `type` 再取 `data`」，加字段不破坏旧解析。

## 3. 消息类型

| type | 方向 | 需要认证 | 说明 |
|---|---|---|---|
| `pair` | 手机 → 车机 | 否 | 用 PIN 换 Token |
| `pair_result` | 车机 → 手机 | — | 配对结果（含 Token） |
| `auth` | 手机 → 车机 | 否 | 用 Token 认证 |
| `auth_result` | 车机 → 手机 | — | 认证结果 |
| `command` | 手机 → 车机 | **是** | 播控指令 |
| `ack` | 车机 → 手机 | — | 指令执行结果，`id` 与请求一致 |
| `state` | 车机 → 手机 | — | 状态推送，主动、无序响应 |
| `ping` / `pong` | 双向 | 否 | 保活 |
| `revoked` | 车机 → 手机 | — | 车机撤销了本机授权，手机须丢弃 Token |
| `error` | 车机 → 手机 | — | 报文层 / 认证层错误，车机不断开 |

未认证连接只接受 `pair` / `auth` / `ping`，其余一律回 `2000 NOT_AUTHENTICATED`。

> **2.0 变更**：`2000` 这条规则实际已经走不到了 —— 连接一建立就是已认证状态，见 §4。

## 4. 连接与认证（2.0：连上即认证）

```
手机                                    车机
 |  连接 ws://ip:18765                    |
 |  <---- state {...} ------------------- |  连上立刻推一份当前状态
 |  -- pair {pin:"", deviceId, ...} ----> |  不校验任何东西，直接回 ok
 |  <---- pair_result {ok:true, ...} ----- |
 |  -- command {action:"play"} ---------> |
 |  <---- ack {ok:true, action:"play"} -- |
 |  <---- state {...} ------------------- |
```

2.0 **取消了 PIN、Token 和设备配对表**：谁连上 18765 谁就能控。

理由是这套东西只在自家车内热点里跑。同一个 Wi-Fi 下的人如果真想发指令，一个 6 位 PIN 拦不住（报文本来就是明文，嗅一下就有），反倒让车主每次上车都要去车里看 PIN、输 PIN。真正的闸门换成了「同时在线台数上限」，默认 4，可调 1~8，超出的新连接会被车机直接关掉。

为了能单独升级车机端不用等手机端一起换，`pair` / `auth` 两个消息仍然保留，车机一律回 `ok`：

- `pair` 回 `{"ok":true,"autoApproved":true,"token":"open",...}`。`autoApproved` 让老客户端跳过 PIN 界面；`token` 是占位值，老客户端会把它存起来下次当 `auth` 发，同样回 `ok`。
- `auth` 回 `{"ok":true,...}`，不校验 Token。
- `revoked` 不再会发出；`2001/2002/2003`（PIN 相关）不再会产生。老客户端里对应的处理分支可以留着，不会触发。

连接数上限的语义：**只拦新连接**。把 4 调成 1 不会把正在放的手机踢下线，只是之后新来的连不上。

## 5. 指令

`command.data.action` 白名单，其余回 `3000`：

| action | args | 说明 |
|---|---|---|
| `play` | — | 播放 |
| `pause` | — | 暂停 |
| `next` / `prev` | — | 切歌 |
| `seek` | `{"positionMs": int}` | 进度跳转；越界回 `3002`，不支持回 `3003` |
| `setVolume` | `{"volume": int}` | 绝对音量；读不到音量能力时回 `3003` |
| `getState` | — | 请求立即推一次 `state`（`reason:"reply"`） |
| `like` | — | 切换当前曲目的红心，没有在播回 `3003`；结果由随后的 `state.liked` 体现 |
| `library` | — | 拉资料库首页，异步回 `library` 消息（喜欢 / 云盘 / 我创建的歌单） |
| `catalog` | — | 拉排行榜 + 推荐歌单，异步回 `catalog` 消息 |
| `search` | `{"q": string}` | 搜歌，异步回 `tracks` 消息（`id` 为 `search:<关键词>`，只带第一页，`total` 是命中总数） |
| `getTracks` | `{"id": string, "offset": int}` | 取一页歌曲（最多 20 首，实际条数见回包 `count`），异步回 `tracks` 消息 |
| `playTracks` | `{"id": string, "index": int}` | 播这个列表的第 index 首，异步回 `ack` |

`id` 取值：`liked`（我喜欢的音乐）、`cloud`（音乐云盘）、歌单数字 id，或带前缀的 `top:<歌单 id>`（排行榜）、`rec:<歌单 id>`（推荐歌单）、`search:<关键词>`（搜索结果，车机侧缓存最近 8 条）。手机端拿到 `catalog` / `tracks` 里的 `id` 原样回传即可，不用自己拼参数。

除 `like` 外这些动作都要发网络请求，所以是**异步 ack**：先回 `library` / `catalog` / `tracks` / `ack`，再做状态推送。

**分页为什么不是固定条数**：单帧上限 8 KB。中文歌名长短差别很大，按条数切不能保证不超——60 首搜索结果实测 10.8 KB，会被发送层整帧丢掉，手机端就永远停在「加载中」。所以每页上限 20 首，服务端再按序列化字节数裁一次（预算 6 KB），回包里 `count` 是这一页实际条数。客户端下一页用 `offset = 已收到的条数`，不会漏也不会重。`tracks` 每条只带 `index / name / artist / durationMs / playable` 五个字段。

`ack` 只表示**指令是否被接受/执行**，不携带播放结果；结果由随后的 `state` 推送体现。这样车机侧「执行 → 必然伴随一次 state」的路径只需实现一次。

## 6. 状态推送

`state.data` 至少含 `playing / title / artist / positionMs / durationMs`；`volume` 能可靠拿到才带，拿不到就不带（**不填假值**，如实记录能力）。`liked` 表示当前曲目是否已在「我喜欢的音乐」里，没有在播时为 `false`。

触发：

- `tick`：每秒一次（进度推进）
- `event`：播放/暂停、切歌、音量变化等，**立即推**
- `reply`：响应 `getState`

`seq` 单调递增，手机侧丢弃 `seq <= lastSeq` 的帧，避免乱序把进度拉回去。同一次切歌不重复推两条 `event`，靠「状态快照比对」去重——只推变化，避免无意义高频消息。

## 7. 错误码

见 `protocol.json.errors`。分段规则：

- `1xxx` 报文层：格式、版本、未知类型 → 不断连接，回错误继续
- `2xxx` 认证层：PIN/Token 相关
- `3xxx` 执行层：不支持的指令、执行失败、越界、能力不存在
- `4xxx` 限流
- `9xxx` 内部异常

## 8. 未定的点（阶段 0 后补）

1. 音量归属：播放器内部音量 vs `AudioManager.STREAM_MUSIC` —— 决定 `setVolume` 走哪条路、`volumeMax` 取多少。
2. `seek` 在现有播放器上是否可靠 —— 若只能跳到「非当前曲目」，则第一版降级为不提供。
3. 车机是否常驻前台服务 —— 决定 `state` 的 tick 从哪个线程/Handler 发。
