# 车机遥控 · 整体设计与实现

> 版本：2.0.0（车机端 versionCode 29）/ 1.8.1（手机端 versionCode 10）
> 适用：`cloudmusic-car`（网易云车机版）+ 局域网手机遥控（App 或浏览器）
> 关联文档：`01-协议-v0.1.md`（报文细节）、`05-网页遥控.md`（mDNS 专项）、`04-使用与构建说明.md`（怎么装）

---

## 0. 一句话概括

车机在 18765 端口同时跑 **WebSocket 服务** 和 **网页静态服务**，并且自己当 **mDNS 应答器**把 `carremote.local` 指向当前热点 IP；手机端用 **App** 连它，或者在浏览器里打开那个域名直接拿到一个同功能的网页遥控器。**没有 PIN、没有配对、连上即控制**，唯一的闸门是「同时在线设备数上限」。

---

## 1. 背景与硬约束

这套东西不是从「我想要个遥控器」出发的，是被一堆现场约束逼出来的形状。理解这些约束，才能理解后面每个设计为什么长这样。

| 约束 | 后果 |
|---|---|
| 车机屏幕 1920×720，横屏，触摸在驾驶位附近 | 后排乘客想切歌必须喊人，才有遥控需求 |
| 车机开热点，**每次开机热点网卡 IP 都变**（不是固定网关） | 不能写死 IP，不能靠「车机地址固定」做任何假设 |
| 车机**没有 adb**、不能 root、不能 `setprop` | 不能装 mDNS 守护进程，不能改系统 hosts，一切必须在 App 内自答 |
| 只有 Windows，没有 Mac / Xcode | 做不了原生 ipa；iOS 侧只能走浏览器 |
| 遥控链路任何异常都不能影响原有播放 | 所有遥控入口全包 `runCatching`，失败只在 UI 提示 |
| 车机 ROM 会冻结后台进程（实测进程状态被打成 `T/stopped`） | 必须有前台服务壳，否则「TCP 连得上但没人应答」 |

最后一条尤其坑：进程被冻结后内核照样回 SYN，连接能建立，应用层却不读数据。手机端的表现是「一直正在连接」，日志里一条都没有 —— 这也是为什么必须有 `RemoteService` 这个前台壳。

## 2. 整体架构

```
┌─────────────────────────── 车机（Android，1920×720） ───────────────────────────┐
│                                                                                │
│  Compose UI ── 设置页「手机遥控」                                                │
│      │  开关 / 自检面板 / 同时在线上限                                           │
│      ▼                                                                         │
│  RemoteServer（单例，进程内）                                                    │
│   ├─ WsServer      18765  TCP，手写 RFC6455 + HTTP 分流                          │
│   ├─ RemoteWeb     同端口返回 assets/remote.html（全内联）                        │
│   ├─ MdnsResponder 5353 UDP，手写 mDNS，应答/宣告 carremote.local                 │
│   ├─ NsdRegistrar  _cloudmusic-car._tcp（给 App 的 NsdManager 用）               │
│   ├─ RemoteLibrary 网易云资料库/搜索/榜单（走车机已登录账号）                       │
│   ├─ PlayerBridge  全工程唯一碰 PlayerHub 的类（主线程）                          │
│   └─ RemoteService 前台壳（防冻结）+ BootReceiver（开机自启）                      │
│                                                                                │
└───────────────┬──────────────────────────────────┬─────────────────────────────┘
                │ ws://<ip>:18765                  │ http://carremote.local:18765
                │                                  │
      ┌─────────▼──────────┐            ┌──────────▼───────────┐
      │ 手机 App（Kotlin）  │            │ 手机浏览器（Safari 等）│
      │ 主动发现/扫描/重连   │            │ 只查一次名字，被动      │
      └────────────────────┘            └──────────────────────┘
```

**三个角色，两种性格：**

- **车机**：被动方。登记服务、应答查询、定时宣告、等连接进来。
- **手机 App**：唯一会「自己找」的。三层兜底（上次地址 → mDNS → 扫网段）。
- **网页**：纯被动。浏览器只在地址栏那一刻查一次名字，之后就是普通 HTTP + WS。

## 3. 关键设计决策

### D1 · 为什么最终形态是网页，而不是 ipa

ipa 必须有 Apple 工具链（Xcode + 签名 + 描述文件），Windows 上无法产出，且免费证书 7 天过期、企业证书要审核。而「车机内置网页」这条路：免签名、不过期、iPhone/Android/平板通吃，代价只是域名解析这一环要自己解决 —— 而这一环正好可以用 mDNS 补上。

### D2 · 为什么网页和 WebSocket 挤同一个端口

手机连的是 `ws://ip:18765`，浏览器打开的是 `http://ip:18765`。如果分两个端口，用户就得记两个数字，且车机防火墙/热点端口转发要开两次。

实现上是在 `WsServer.serve()` 里**先读完整请求头再决定走哪条路**：

```
读请求头（到 \r\n\r\n 为止）
  ├─ 含 Sec-WebSocket-Key  → 回 101 Switching Protocols，升级成 WS，创建 Conn
  └─ 不含                   → 把请求头交给 RemoteWeb.handle()，回 200 + HTML，关连接
```

关键细节：`Conn`（带写线程和发送队列的对象）**推迟到确认是 WS 之后才创建**。否则每个 HTTP 请求都会白起一个写线程，浏览器刷新几次就攒一堆。

### D3 · 为什么要手写 mDNS，不用 NsdManager

`NsdManager` 能注册 `_cloudmusic-car._tcp`，App 也能发现 —— 这条路径是通的，手机 App 就靠它。但 **Safari 在地址栏输入 `carremote.local` 时，问的是系统 mDNS 解析器**，它只会去查 5353 端口的 **A 记录**，而 `NsdManager` 注册的服务不提供主机名 A 记录（它只发布 PTR/SRV/TXT）。

所以必须自己绑 5353 当应答器，直接回答 `carremote.local` 的 A 记录。这也解释了为什么「IP 能进、域名进不去」在早期版本是个必然现象。

### D4 · 为什么靠「定时宣告」而不是「等别人来查」

这是域名「过一会就连不上」的根治点。

A 记录 TTL 120 秒，一过期对端就必须重新查询；而**查询这条路在车机热点上不可靠**（Wi-Fi 驱动过滤组播、AP 模式下的 IGMP snooping、5353 被系统 mDNS 抢先绑定后收包被分走）。于是「启动时那一次宣告还能吃到」就退化成「两分钟后再也进不去」。

改成每 **45 秒** 主动重播一次，对端缓存永远不到期，就绕开了「收查询」这个不可靠环节。TTL 保持 120 不动 —— 不赌客户端尊重大 TTL。

### D5 · 为什么把 PIN 和配对删掉

原设计是 6 位 PIN + Token 落库。实际使用中：每次上车要跑到前面看 PIN，热点 IP 又每次变，摩擦远大于收益；而同一个 Wi-Fi 下真想发指令的人，6 位数字也挡不住。

2.0 起改为「连上即认证」，唯一闸门是**同时在线设备数上限**（默认 4，可调 1~8）。这个闸门挡的是数量，不是身份 —— 这点必须说清楚，它是设计取舍，不是安全承诺。

协议层保留了 `pair` / `auth` 两个消息，一律回 `ok`，为的是**车机端能单独升级**，不用等手机端一起换。

### D6 · 为什么状态是 1 秒推一次 + 节流

进度条要平滑，所以 1 秒一次 tick。但暂停且内容没变时推同样一份 JSON 是纯浪费（还费电），于是用 `playing|title|artist|duration|volume|liked` 拼一个 key，key 没变且不在播放就跳过这次 tick。

指令生效时**立即**推一次（`reason=event`），不等下一个 tick，所以按下去是跟手的。

### D7 · 为什么列表分页是 40 首 + 7 KB 预算

单帧上限 8192 字节（`MAX_FRAME_BYTES`），而中文歌名长短差异极大。按条数切不能保证不超帧 —— 早期 60 首一帧 10859 字节，超限被静默丢掉，手机端表现就是「搜索永远转圈」。

v2.2 把每页从 20 首提到 40 首（一屏大约 7 行，20 首要划两次才够看）。常见长度（歌名 + 歌手 20 来字）下正好装下 40 首；遇到全是长名字的列表会自动少放几首，仍然双重约束：先按 40 首切，再按序列化字节数裁到 7000 以内。两端的分页偏移都按「已收到的条数」算，所以页大小变了也不用改协议。

超限不再静默丢包，回明确的错误。手机端还有 15/20 秒超时兜底。

## 4. 协议

### 4.1 信封

```json
{ "v": 1, "type": "command", "id": "r12", "ts": 1699000000000, "data": { } }
```

- `v` 必须等于 1，否则回 `1001`；
- `id` 请求方生成，响应原样带回（`state` 推送不带 id）；
- 单帧 ≤ 8192 字节，文本帧，不做分片。

### 4.2 消息类型

| type | 方向 | 说明 |
|---|---|---|
| `ping` / `pong` | 双向 | 应用层心跳，`pong` 回 `serverTs` |
| `pair` / `pair_result` | C→S / S→C | 兼容层，一律 `ok`，带 `autoApproved:true` |
| `auth` / `auth_result` | C→S / S→C | 兼容层，一律 `ok` |
| `command` / `ack` | C→S / S→C | 播放控制，`ack.ok` 表示成败 |
| `state` | S→C | 播放状态，带自增 `seq` |
| `library` | S→C | 资料库首页（喜欢/云盘/我的歌单） |
| `catalog` | S→C | 排行榜 + 推荐歌单 |
| `tracks` | S→C | 列表内容（搜索/歌单/榜单通用） |
| `error` | S→C | 错误码 + 文案 |

### 4.3 指令

| action | args | 说明 |
|---|---|---|
| `play` / `pause` | — | 播放/暂停 |
| `next` / `prev` | — | 切歌 |
| `seek` | `positionMs` | 跳转，无媒体时回 `3003` |
| `setVolume` | `volume` | 0~volumeMax |
| `getState` | — | 立即回一份 `state` |
| `like` | — | 红心切换（乐观更新，失败回滚） |
| `library` | — | 资料库首页 |
| `catalog` | — | 榜单 + 推荐 |
| `search` | `q` | 搜索，空关键词回 `1000` |
| `getTracks` | `id`, `offset` | 分页取列表 |
| `playTracks` | `id`, `index` | 从某列表第 index 首开始播 |

列表 `id` 用前缀区分来源，手机端原样回传即可：`liked` / `cloud` / 纯数字歌单 id / `top:<id>` / `rec:<id>` / `search:<关键词>`。

### 4.4 错误码

| 码 | 含义 | 典型场景 |
|---|---|---|
| 1000 | 报文非法 | 不是 JSON、缺必填参数 |
| 1001 | 版本不支持 | `v != 1` |
| 1002 | 未知类型 | |
| 2000 | 未认证 | 2.0 起基本不会出现，留着兜底 |
| 3000 | 不支持的动作 | |
| 3001 | 执行失败 | 播放器抛异常 |
| 3002 | 参数越界 | 负数进度、音量超上限 |
| 3003 | 当前不可用 | 没歌却 seek、没音量控制 |
| 4000 | 限流 | 预留给后续 |
| 9000 | 内部错误 | |

`2001`~`2006`（PIN/Token 相关）在 2.0 保留定义但不再产生，只为旧客户端兼容。

## 5. 车机端模块

| 文件 | 职责 | 线程 |
|---|---|---|
| `WsServer.kt` | 监听、HTTP/WS 分流、握手、帧编解码、发送队列 | 每连接 1 读 + 1 写 |
| `RemoteServer.kt` | 协议分发、状态推送、在线列表、watchdog | 定时器 2 线程 + 主线程 |
| `RemoteWeb.kt` | 返回 HTML / icon，字节缓存 | 连接线程 |
| `RemoteLibrary.kt` | 资料库 / 歌单分页 / 搜索，LRU 缓存（份数 + 字节双闸门） | IO 线程 |
| `RemoteLibrary.kt` | 资料库/搜索/榜单，IO 协程 | `Dispatchers.IO` |
| `MdnsResponder.kt` | 5353 应答 + 保活宣告 | 独立守护线程 |
| `NsdRegistrar.kt` | `_cloudmusic-car._tcp` 注册 | 系统回调 |
| `PlayerBridge.kt` | 唯一碰 `PlayerHub` 的地方 | **必须主线程** |
| `RemotePrefs.kt` | 上面限持久化（1~8） | — |
| `RemoteService.kt` | 前台服务壳，防进程冻结 | — |
| `BootReceiver.kt` | 开机自启 | 广播 |

**线程模型要点：**

- 播放器（ExoPlayer）只能在主线程碰，所以 `handleCommand` 把执行体 `main.post` 过去，**ack 在同一个 Runnable 里发**，保证「执行 → 回执」顺序不乱；
- 资料库要发网络请求，走异步分支，绝不阻塞读线程；
- 发送侧每连接一个有界队列 + 写线程，慢客户端不会拖住别人；
- `watchdog` 每 5 秒：刷新 UI、`mdns.refresh()`、踢掉 90 秒没说话的空闲连接。

**生命周期：**

```
开机 → BootReceiver（若上次开关是开的）→ RemoteServer.start()
应用在前台 → 设置页开关 → start()/stop()
start() → WsServer.bind(18765) → NsdRegistrar.register() → MdnsResponder.start() → 定时器 → 前台服务
```

`start()` 全程包 `runCatching`：端口被占用只把 UI 的 `error` 置为「端口 18765 被占用」，不抛给调用方。

## 6. 手机端设计

### 6.1 状态机

```
        ┌──────────┐   连接成功+去抖 400ms   ┌──────────┐
        │Connecting├──────────────────────►│  Ready   │
        └────┬─────┘                       └────┬─────┘
             │ 失败/超时                        │ 断开
             ▼                                  ▼
        ┌──────────┐   指数退避 1→15s      ┌──────────┐
        │  Failed  ├──────────────────────►│ 重连中    │
        └──────────┘                       └────┬─────┘
                                                │ 连续 3 次仍失败
                                                ▼
                                         回到连接页
```

### 6.2 启动时序（这是「刚启动反复跳」的修复核心）

| 时刻 | 动作 |
|---|---|
| 0 s | 有上次地址就直连；同时开始 NsdManager 发现 |
| 0~2.5 s | 只允许这一条连接存在 |
| 2.5 s | 若仍未 `Ready`，扫本机 `/24` 网段找 18765 |
| 扫到 | 再 `connect()` 一次（换目标，先关旧连接） |

之前是「直连」和「扫描」同时开跑、扫完无条件再连一次，**两条 socket 同时活着且共用一个 `socket` 字段**，任一条抖一下就把状态改成 `Failed`，界面就在「连上/断开」之间弹。现在用三道锁：

1. **connect 幂等**：同目标已在连就不再开新的；
2. **代次（generation）**：每条连接带 `gen`，过期回调直接丢弃 —— 旧 socket 的 `onFailure` 再也打不掉新连接的状态；
3. **Ready 去抖 400 ms**：授权成功不立刻跳面板，等第一条 `state` 或 400 ms 到点才切。

### 6.3 网络参数

| 项 | 值 |
|---|---|
| 扫描并发 | 每批 64 个 IP |
| 单 IP 超时 | 350 ms（整体约 1.4 s） |
| 重连退避 | 1 → 2 → 4 → 8 → **15 s 上限** |
| 静默断线容忍 | 3 次，超过才退回连接页 |
| 应用层心跳 | **25 s** |
| OkHttp 协议层 ping | 20 s |
| 网络变化 | `ConnectivityManager` 回调，恢复即重连 |

心跳那条是后补的：车机端「90 秒没说话就断开」看的是**应用层消息**，而暂停播放时状态推送被节流成一条不发，OkHttp 的协议级 ping 由对端 WS 层自己回 pong、不进业务计时 —— 结果就是暂停放着不动一分半被踢，然后重连。

网络变化监听（`NetWatcher`）是 1.8.3 补的：此前断网/切 Wi-Fi 只能等退避定时器，最长 15 秒才轮到下一次重试。现在系统回 `onAvailable` 就把退避打回 1 秒并立刻重连，回 `onLost` 则主动断开（不等 OkHttp 自己超时）。两端对称：车机端 `NetworkMonitor` 负责重建 mDNS 与推送新地址。

### 6.4 界面

- **连接页**：发现的设备列表（点一下连）、手动 IP:端口、扫描按钮；
- **遥控页**：封面区标题/歌手、进度条、上一首/播放/下一首、音量步进、红心、搜索、资料库、榜单、推荐；
- **资料库页**：三个入口 + 歌单列表 + 加载更多（每页 20）。

## 7. 网页端

`assets/remote.html`，774 行单文件，**零外链资源**（图标全内联 SVG，样式全内联），弱网一次加载完就能离线渲染骨架。

功能与 App 对齐：播控、进度拖拽、音量、红心、搜索、资料库（喜欢/云盘/歌单）、排行榜、推荐歌单、曲目列表全屏 sheet。

实现要点：

| 点 | 做法 |
|---|---|
| 布局 | 单页可滚动（早期 `overflow:hidden` 导致首屏只够播控） |
| 曲目面板 | 独立全屏 sheet，偏移按**已收到条数**算，不按页号 |
| 红心 | 先本地翻转再发指令，由 `state` 校正（避免等一个来回） |
| 过期回包 | 校验 `id`，不匹配的 `tracks` 直接丢（否则旧列表会覆盖新面板） |
| 重连 | 1 → 2 → 4 … **10 s 上限** |
| 心跳 | 每 **20 s** 一条 `ping`（所以网页没有 90 秒被踢的问题） |
| 地址 | 页脚显示 `carremote.local:18765`，与 IP 无关 |

## 8. mDNS 专章

### 8.1 为什么要「手写」

见 D3。补充：车机没有 adb，不能 `setprop`、不能装 `avahi`/`mdnsd`，也没有 root，所以只能在应用进程里自己开一个 5353 的 `MulticastSocket`。

### 8.2 报文规则（每一条都是踩坑换来的）

| 规则 | 原因 |
|---|---|
| 只答 **A**（type 1），`ANY` 也按 A 答 | 车机只有 IPv4，答 AAAA 是撒谎 |
| 纯 AAAA 查询 → 回 **NSEC**（type 47，位图 `00 01 40`） | 明确告知「这个名字没有 IPv6」，免得对方等超时 |
| 有 A 的包里**绝不掺** NSEC | 一条怪记录会把整包带坏 |
| 解析包里**全部** question，不只看第一条 | iOS 常把 `AAAA` 和 `A` 塞进同一包（QDCOUNT=2）且 AAAA 在前；旧代码只看第一条就 return，于是「收 N / 回 0」 |
| 一律**组播**回 224.0.0.251:5353 | 单播包 TTL 是默认 64，而 RFC 6762 要求 255，iOS 对 TTL≠255 直接静默丢 |
| 另补一份**单播**给提问者 | 热点若挡组播，单播是唯一可能漏过去的路径（多一个包换一个机会） |
| 压缩指针偏移**按回包重算** | 只回显部分 question 时偏移变了，照抄原包偏移必然指向垃圾 |
| 必须持 `MulticastLock` | 部分机型 Wi-Fi 驱动默认过滤组播 |

### 8.3 保活

```
绑定 5353 → 宣告 1 次
  ↓
receive(超时 1s)
  ├─ 收到查询 → 判断类型 → 应答
  └─ 超时      → keepAlive()：距上次宣告 ≥ 45s 就再宣告一次
```

宣告包是 `QDCOUNT=0, ANCOUNT=1` 的 43 字节，不含任何尾填充。

三处必须守住，否则保活会静默失效：

| 坑 | 后果 |
|---|---|
| `receive` 死等没有超时 | 没人查时线程永远阻塞，保活根本不转 |
| `refresh()` 拿 `hostIp`（会被收包逻辑实时改写）当基准 | 永远「没变」，socket 再也不重建 |
| `stop()` 后旧线程还卡在 `receive` | 新旧两个 worker 抢 5353，故加 `generation` 代次 |

### 8.4 自检面板（唯一的现场验收手段）

```
mDNS 就绪 · ap0 · 收 12 / 回 12
域名保活：已宣告 47 次 · 上次 43s 前
最近查询：A carremote.local · 已答
```

- **已宣告 N 次**：必须一直在涨；
- **上次 Xs 前**：正常在 45 上下，> 60 就是保活停了；
- **收 N / 回 N**：收了不回说明类型判断错了（历史上就是只看第一条 question 那次）。

## 9. 安全模型

**明确说清楚，别误会：**

- 无 TLS，无 PIN，无 Token。同网段任何人连上 18765 就能发指令，能看歌单。
- 唯一的限制是**同时在线上限**（默认 4，可调 1~8），它挡数量不挡身份。
- 设计前提是「车内可信网络」。**不要把 18765 映射到公网**，不要在公共 Wi-Fi 开遥控。
- 车机端不落任何设备标识（2.0 起连设备表都删了），手机端只存「上次连的地址」。

这套取舍是刻意的：车机热点 IP 每次变，任何需要「事先同步一个秘密」的方案都会退化成「每次上车跑去前面抄数字」。

## 11. 排障对照

| 现象 | 先看什么 | 处理 |
|---|---|---|
| IP 能进、域名进不去 | 自检面板「收/回」「已宣告」 | 宣告不涨 → 重启遥控服务；收了不回 → 类型判断问题 |
| 域名过一会失效 | 「上次 Xs 前」 | 一直在涨但 X > 60 → 保活循环没转 |
| 能连上但界面不动 | 车机进程是否被冻结 | 必须挂前台服务 |
| 搜索一直转圈 | 车机日志 `frame too large` | 分页/预算失效 |
| 暂停一分半后自动重连 | 心跳是否在发 | 25 s 心跳缺失 |
| 刚打开反复跳「连上/断开」 | 是否有两条 socket | 代次校验 + 幂等 connect |
| 连上几秒就断 | 「同时在线 N / M」 | 上限调大或断开一台 |
| 曲目列表错乱 | 回包 `id` 校验 | 旧列表覆盖新面板 |

## 13. 已知限制

1. **未在真车验证**：没有 adb 设备，所有结论来自离线自检 + 浏览器无头截图。mDNS 能否穿过真实热点网卡、熄屏后前台服务能否常驻、车机功放音量是否真的跟着变，都需要上车实测。
2. **mDNS 只在 IPv4 单网卡假设下工作**：多网卡（Wi-Fi + 有线）时按「收包那块网卡」取地址，理论上对，但没测过。
3. **网页端无本地存储**：刷新即重连，歌单状态不缓存，每次都要重新拉。
4. **资料库依赖车机账号**：车机没登录网易云时，资料库/搜索会回「车机还没登录」。
5. **无鉴权**：见第 9 节，这是设计取舍不是遗漏。
