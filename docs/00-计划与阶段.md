### 实际勘察结果与原先假设的差异

1. **不缺 `cloudmusic-car`** —— 用户给了仓库地址，直接 clone（此前本机确实没有）。
2. **不是 `no Gradle` 场景** —— 原工程是 Kotlin + Compose + Gradle 8.14.5。D1 决策（手工 aapt2 + javac）**作废**，改为正常 Gradle 构建；本机补了 JDK 21 与自建 SDK。
3. **不用自己写 WebSocket 客户端** —— Compose 都能编，OkHttp 也就是一行依赖，手机端直接用 OkHttp（D2 只对车机端成立，车机端仍为手写实现，避免给宿主 APK 加依赖）。
4. **播放器是进程级单例** —— 比原先假设的更好：遥控服务同进程直调，不需要 Binder、不需要新 Service（D5 更简化）。
5. **`compileSdk` 36 → 35**：AGP 8.7.3 上限就是 35，且本机 SDK 只到 35。

## 阶段 0 要产出什么

不是"读完源码写感受"，而是四份可执行结论（模板见 [`02-阶段0-勘察清单.md`](./02-阶段0-勘察清单.md)）：

1. 播放器实例：类型（静态单例 / Binder / MediaSession / 全局 Application 持有）、创建点、线程要求。
2. 控制入口：play/pause/next/prev/seek/音量 各自现有方法签名。能直接调的直接调，不能的记「不支持」。
3. 状态来源：当前曲目/歌手/进度/总时长 从哪个对象取，是否有现成回调。
4. 挂载方式：遥控服务依附现有播放 Service，还是独立；对应目标车机 Android 版本的后台限制。

## 技术决策（先定，后可推翻但要有理由）

### D1 · 不引 Gradle，沿用本盘已验证的手工构建链

本机没有 Gradle 与 Android Studio，`D:\车机` 下其它工程（联动、CarManager）都是 `aapt2 + javac + d8 + zipalign + apksigner` 手工打包并验收通过的。沿用同一套：

- 工具：`~/.workbuddy/binaries/jdk/jdk-17.0.20.1+1/bin/javac`、`~/.workbuddy/binaries/android/android-35/android.jar`、`~/.workbuddy/binaries/android/android-14/{aapt2,d8,zipalign,apksigner}`（见 `_工具/env.sh`）。
- 语言用 **Java**，不用 Kotlin —— 免 kotlinc。
- UI 用 **原生 View + XML**，不用 Compose —— Compose 必须有 Gradle 和一堆 androidx 依赖，本机拉不到。

代价：没有依赖管理，所有库得手写或 vendor。这直接引出 D2。

### D2 · WebSocket 自己实现，不引 OkHttp

需求里建议 OkHttp WebSocket，但它是 Gradle 依赖。本机离线、无 Gradle，vendor 一个 okhttp + okio 进来还要处理它的 `okhttp-ws` 兼容和体积，不划算。

自实现范围很小且可控：

- 服务端：握手（`Sec-WebSocket-Accept`）+ 文本帧解掩码 + close/ping 帧，协议简单，约 300 行。
- 客户端：握手 + 掩码发送 + 收帧，约 250 行。

只支持「单帧文本、≤8 KB」，够本案用；分片、二进制帧明确不支持并回错误。这是有意识的能力裁剪，不是遗漏。

### D3 · mDNS 用系统 `NsdManager`，不引第三方库

Android 原生就有。注册 `_cloudmusic-car._tcp`，手机 `discoverServices` 解析地址端口。`MulticastLock` **先不预设必需**，阶段 1 在目标车机实测：发现不到再加。

发现不可靠时的兜底顺序：手动 IP → 车机 UI 显示当前 IP 与端口（最土但永远可用）→ 再考虑 UDP 广播。设备发现不得阻塞主体功能，这条兜底路径从第一版就保留。

### D4 · PIN 与 Token 的存储

- 车机侧只存 `SHA-256(token)`，不存明文；PIN 只存内存，进程重启即失效。
- 手机侧 Token 存 `SharedPreferences(MODE_PRIVATE)`。没有 androidx.security 就没有 `EncryptedSharedPreferences`，所以**如实标注**：root 设备上可读。第一版接受，文档写明，不用"已加密"粉饰。

### D5 · 遥控服务默认不新开前台服务

先看现有 Service。若播放本身已在长驻 Service 里，遥控服务挂它的生命周期即可，不额外加一个前台通知骚扰用户。只有在实测「屏幕关闭后 socket 被挂起」时才升级为前台服务，并且做成可开关。

## 风险与对策

| 风险 | 对策 |
|---|---|
| `cloudmusic-car` 是第三方闭源 APK，没有源码 | 退化为「apktool 反编译 + 注入 smali/Java 模块」，本盘已有成熟做法（联动工程）。代价是不能改原逻辑，只能加 |
| 播放器是某家 SDK 的对象，没有公开控制方法 | 只能走 MediaSession / 系统媒体按键广播；如实记录能力边界，不模拟点击 |
| 车机 Android 版本老，`NsdManager` 有 bug | 阶段 1 实测；不行就走手动 IP |
| 手写 WebSocket 有协议细节坑（掩码、分片） | 阶段 1 用 PC 端脚本对打，覆盖握手/掩码/大帧/半包 |
| 车机熄屏后 socket 断 | 阶段 1 实测；必要时前台服务 + 保持 Wi-Fi 锁 |
