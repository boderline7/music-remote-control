# 05 · 网页遥控（iPhone / 任意浏览器）

> 一句话：车机端自己提供一个网页遥控器，手机浏览器打开 `http://carremote.local:18765/` 就能用，不用装 APK、不用签名、不会过期。

## 为什么要有它

iOS 没有 Mac 就编不出 ipa，而网页版不需要任何打包和签名。代价是浏览器拿不到「网段扫描」「Bonjour 发现」「读默认网关」这些原生能力，所以地址必须固定 —— 这一条由车机端的 mDNS 解决。

## 地址

| 用途 | 地址 |
|---|---|
| 日常使用（书签 / 添加到主屏幕） | `http://carremote.local:18765/` |
| 打不开时的备用 | 车机设置页上显示的 `http://<当前热点 IP>:18765/` |

`carremote.local` 是 mDNS 名字，永远指向车机**当前**的热点 IP。车机开热点时网段每次开机都可能变（`192.168.x.1` 的 x 随机），IP 会变但名字不变，所以书签不会失效。

第一次打开时 Safari 会问「允许“Safari”访问本地网络上的设备？」，点**允许**。误点了拒绝可以去：设置 → 隐私与安全性 → 本地网络 → Safari，重新打开。

## 网页端能做什么

和 Android 遥控 App 基本对齐（1.9.0 起）：

| 区块 | 能力 |
|---|---|
| 正在播放 | 曲名、歌手、爱心（加入 / 取消我喜欢的音乐）、进度条拖动 seek、上一首 / 播放暂停 / 下一首 |
| 音量 | 滑块 + 减 / 加按钮（步进 = 音量上限 / 15） |
| 搜索 | 输入歌名或歌手，回车或点放大镜，结果直接点播 |
| 资料库 | 我喜欢的音乐、音乐云盘 |
| 为你推荐 | 每日推荐、心动模式（2.2.1 起，排在资料库下面、自建歌单上面） |
| 歌单 | 我创建的歌单、推荐歌单（默认只铺前 5 个，点「展开全部」看完整列表） |
| 榜单 | 排行榜、推荐歌单（点进去按页加载） |

歌单和搜索结果从底部面板弹出，每页按字节预算最多 40 首，底部「加载更多（40/128）」显示已加载 / 总数，偏移用「已收到的条数」算，不会漏也不会重。

「每日推荐」和「心动模式」在车机上本来就没有网易云的歌单 id（一个是当天推荐、一个是拿红心做种子现生成），所以车机端把它们当作两个**虚拟列表 id**（`daily` / `heartbeat`）挂进同一套 `getTracks` / `playTracks`：
网页和手机端点进去照样是一个列表，看队列、点某一首，跟真歌单没有区别；车机那边播放心动模式时带上 `PlayMode.HEARTBEAT`，和首页点卡片的行为一致。所有列表都由车机用**已登录的账号**去拉，网页不需要登录网易云。

网页和 IP 访问是同一套协议、同一个端口：WS 走 `/`，静态页靠请求头里有没有 `Sec-WebSocket-Key` 分流。所以网页和行为跟 App 完全一致（包括喜欢、搜索、榜单这些后加的动作）。

## 车机设置页能看到的自检

「手机遥控」页里有一块 `手机浏览器遥控`，显示：

- 固定地址 `http://carremote.local:18765`
- mDNS 状态：`mDNS 就绪 · wlan1 · 收 34 / 回 34`（绿色）或异常原因（橙色）
- 最近一次查询：`A carremote.local`，能看到手机到底问了什么
- 备用地址：当前热点 IP

「收 / 回」是两个数：收到了多少次名字查询、回了多少次答案。手机打开网页时两个数会一起涨，说明问答都通。

## mDNS 必须守的四条规矩

踩过两次，两次都是「车机说回了、iPhone 没收到」，因为 iOS 的 mDNSResponder 对不合规的包一律静默丢弃，不报错也不重试：

| 规矩 | 不守的后果 | 现在的做法 |
|---|---|---|
| 一个查询包里可能有多条 question，必须全看 | 只读第一条时，遇上 iOS 把 AAAA 放前面就直接跳过了 A —— 表现就是「收 N / 回 0」 | 解析全部 question，只要有 A 就答 A |
| 应答必须发到 `224.0.0.251:5353`（组播） | iOS 只认组播应答，单播回去的包它不收 | 一律组播回复（再补一份单播，赌热点挡组播的情况） |
| 报文的 IP TTL 必须是 255 | `MulticastSocket` 只能设多播 TTL，单播包仍是默认 64，被整包丢弃 | 走组播，TTL 恒为 255 |
| 不要回「空的 AAAA」 | 空答案会被当成「这个名字不存在」，整个解析直接判死 | 纯 AAAA 查询回一条 NSEC（`有 A、没有 IPv6`），有 A 的包里绝不掺 |

第 1 条是 1.8.0 修的那个：之前只看第一条 question，而 iOS 常常把 `AAAA carremote.local` 和 `A carremote.local` 塞进同一个包，顺序还不固定。于是「收」涨了、「回」一直是 0，域名自然打不开。

## 2.0 的关键修复：域名不能靠「有人来问」才活着

1.9 的域名有个很典型的症状：**刚重启服务能打开，过一两分钟就再也进不去**，而同一时刻用 IP 访问完全正常。

原因不是应答写错了，而是**应答这条路本身不可靠**：

- `carremote.local` 的 A 记录 TTL 只有 120 秒，这是 RFC 6762 对「地址可能会变」的记录的推荐值；
- 120 秒一到，手机侧缓存过期，必须**重新发查询**才能继续解析；
- 而查询走的是组播 5353，在车机热点网卡上，收方向经常是断的（驱动过滤组播、AP 模式下的 IGMP snooping、5353 被系统 mDNS 抢先绑定后收包被分走，都见过）；
- 于是「启动时那一次宣告还能吃到」=「刚启动能打开」，之后就是「两分钟后再也进不去」。

修法不是继续抠应答细节，而是**绕开查询**：改成每 45 秒主动重播一次 A 记录，让对端缓存永远不到期。

| 项 | 值 | 为什么 |
|---|---|---|
| TTL | 120 秒（不变） | 保持符合规范，不改成一个偏大的值去赌客户端尊重 |
| 重播间隔 | 45 秒 | 一个 TTL 窗口内至少刷两次，丢一个包还有下一次 |
| 触发方式 | 独立宣告线程，5 秒一跳、满 45 秒才发 | 2.1 起从收包循环里拆出来：发送抖动不该连带把正常的回包 socket 拆掉 |
| 失败处理 | 连续 3 次发不出去才重建 socket | 偶发一次发送失败很常见（组播本来就会丢），立刻重建反而更慢 |

代价是每 45 秒一个 43 字节的组播包，可以忽略；换来的是域名解析不再依赖双向组播通。

设置页那行「域名保活：已宣告 N 次 · 上次 Xs 前」就是给它看的：**N 应该一直在涨，X 应该始终在 45 上下**。X 到 60 以上说明保活停了，那时域名必然会在两分钟内失效，重开一次遥控服务即可。

顺带修了两个会让保活失效的坑：

- `refresh()` 原来拿 `hostIp` 当「地址有没有变」的基准，而 `hostIp` 会被收包逻辑实时改写，等于永远相等，socket 再也不会重建。现在单独用 `boundIp`（只由绑定 socket 的那个线程写）。
- `stop()` 之后旧 worker 可能还卡在 `receive` 里，紧接着 `start()` 又把 `running` 置回 true，旧线程就活过来和新线程抢 5353。现在加了代次 `generation`，旧线程一发现自己过期就退出。

另外仍是：启动时和 IP 变化时 announce 两次（背靠背，UDP 会丢包）；每 5 秒体检一次网卡，换网卡或换地址自动重建监听。

## 2.2 审计：IP 变了之后，到底能不能自己恢复

这一节是照着「热点 IP 不固定」这个真实前提逐条核过的结论，不是设想。

### 已经具备的（审计前就有，没重复开发）

| 能力 | 实现 |
|---|---|
| 找到热点网卡 | `pickInterface()` 遍历所有网卡，按 `ap*`/`softap` > `swlan*` > `wlan*` > `eth*` > 其它打分选最高，再对 `x.x.x.1`（网关）和 `192.168.x` 加分 |
| 检测 IP 变化 | 每 5 秒 `refresh()` 比较 `interfaceName` 和 `boundIp`，不一致就重建 socket |
| 旧 socket / 旧线程退出 | `forceRebuild()` 关 socket 让 `receive` 抛异常跳出；`generation` 代次保证 `stop()` 后的旧线程不会再抢 5353 |
| 重新宣告新地址 | 新 socket 一 bind 完就背靠背发两份 A 记录（带 cache-flush），不等 45 秒 |
| 网络事件提前触发 | `NetworkMonitor` 监听 WiFi/以太网/蜂窝的可用性变化，回调里立刻重建 |
| HTTP/WS 不受 IP 影响 | `ServerSocket` 绑的是 `InetSocketAddress(port)`（通配 `0.0.0.0:18765`），从未绑过具体 IP |
| mDNS 失败不影响直连 | 遥控服务先起 18765，再起 mDNS，mDNS 起不来只是自检面板报错 |

### 审计发现并修掉的四个真问题

**1. 设置页显示的 IP 可能是错的（最影响使用）**

`localIpv4()` 原来的写法是「取第一个名字以 `wlan` 或 `ap` 开头的网卡地址」。车机一边连着 WiFi、一边开热点时两块网卡都命中，而枚举顺序不保证，于是页面经常显示 `wlan0` 的地址 —— 手机在热点网段，照着这个 IP 输进去必然连不上。这直接违反「IP 直连作为兜底」的定位。

现在：优先取 mDNS 已经选定的热点地址，取不到时用**同一套打分函数**（`MdnsResponder.scoreOf`）自己算。页面显示和 A 记录保证同源。

**2. 重建空窗里会把旧 IP 再喊一遍**

宣告线程是独立跑的（5 秒一跳）。`forceRebuild()` 只关了 socket、清了 `lastAnnounceAt`，但 `boundIp` 还留着旧值 —— 空窗里宣告线程醒来，拿着旧 IP 又发了一次带 cache-flush 的 A 记录，手机刚拿到新地址又被改回旧地址。表现就是「域名一会儿能进一会儿不能」。

现在 `forceRebuild()` 同时清掉 `boundIp` 和 `announcedIp`，宣告线程读不到地址就跳过，等新 socket 起来再喊。

**3. 熄屏亮屏后 mDNS 可能「假活」**

车机熄屏时常把 AP 关掉省电，亮屏再起来时网卡可能换名、换网段，内核也会清掉之前的组播加入关系。而我们的 socket 不一定报错 —— 线程活着、`isRunning()` 为 true，但什么都发不出去。原来只靠「宣告停滞 135 秒就重建」兜底，用户亮屏就想连，等不了两分钟。

现在注册 `ACTION_SCREEN_ON`：亮屏时主动查一次，**90 秒没成功宣告过就重建**（判据是 `needsRebuild()`，不是看 socket 在不在 —— 假活时 socket 是在的）。熄屏也记一条日志，方便对着导出日志看时间线。

**4. accept 线程静默退出后端口「能连上但握不上手」**

`acceptLoop` 遇到 `IOException` 只 `break`，没把 `running` 置 false。结果是 `isRunning()` 永远返回 true，健康检查看不出问题，而实际上已经没人 accept 了。现在异常退出会把状态标成停止，watchdog 每 5 秒检查一次并自动重启监听（30 秒内只试一次，避免端口真被占用时刷错误）。

### 手机端的配合（IP 变了怎么找回车机）

App 记的是上次的 IP，IP 一变就永远连不上，原来的退避重试会一直对着旧地址重试到 15 秒一次。现在连续失败 3 次（约 7 秒）就做一次兜底发现：

1. 先解析 `carremote.local`（Android 12+ 的解析器能走 mDNS，1.5 秒超时）；
2. 解析不到、或解析出来还是老地址，就扫本机所在 /24 的 18765 端口（约 1.4 秒）；
3. 只有找到**不同**地址才切过去；找到同一个说明车机真的不在，交回原来的退避继续等。

网页端做不了这件事（JS 不能强制重新解析域名），所以改成「说人话」：连续 4 次重连失败就把状态换成「连不上车机 · 地址可能已变，下拉刷新或重开本页」，同时把退避上限从 10 秒压到 5 秒，这样浏览器 DNS 缓存（我们发的 TTL 是 120 秒）一过期就能立刻恢复。

### 还没验证的

以上全部只做了静态检查与编译，**没有真机验证**。上车要看的三个点：IP 变化后 5 秒内自检面板的 `mDNS` 地址是否跟着变（不用手动重开服务）、亮屏后第一次刷新网页能否直接进、以及「本机地址」和域名解析出来的 IP 是否始终一致。

## 打不开时按这个顺序排查

1. **手机连的是不是车机热点**：不是同一个局域网肯定不行。
2. **车机设置页那行字是不是绿色**：橙色说明 mDNS 没起来，看它给的错误（常见是热点还没分配网卡、或组播锁没拿到）。
3. **换成备用地址**（`http://<IP>:18765/`）试一次：
   - 备用地址也打不开 → 是 HTTP 端口没通，不是 mDNS 的问题。
   - 备用地址能开、域名打不开 → 往下看第 4 条。
4. **看「收 / 回」两个数**（重启 App 后清零，所以先在手机上刷新几次页面再看）：
   - `收 0` → 手机的查询没到车机：iOS 本地网络权限没给（设置 → 隐私与安全性 → 本地网络 → Safari），或热点开了 AP 隔离。
   - `收 N / 回 0`，且「最近查询」写的是 `AAAA carremote.local · 回 NSEC` → 手机只问 IPv6。1.8.0 起会给 NSEC 让它立刻回落，仍然打不开就说明 iOS 侧缓存了旧的失败结果：开一次飞行模式再关掉，或换个 WiFi 名重连一次。
   - `收 N / 回 0`，且「最近查询」写着 `· 忽略` → 手机问的类型不是 A/AAAA，把这行记下来（说明遇到没覆盖的解析路径）。
   - `收 N / 回 N` 且数字在涨，域名还是打不开 → 基本只剩 iOS 本地网络权限这一种可能，去系统设置里关掉 Safari 的本地网络再重新打开，让它重新弹一次授权。

## 实现位置

| 文件 | 作用 |
|---|---|
| `assets/remote.html` | 整个遥控页面：内联 CSS/JS，无外链，一次加载完 |
| `remote/MdnsResponder.kt` | 应答 `carremote.local` 的 A 记录；IP 变了答案跟着变 |
| `remote/RemoteWeb.kt` | 与 WebSocket 共用 18765，按请求头分流；提供 `/` 和 `/icon.png` |
| `remote/WsServer.kt` | 读请求头后判断：有 `Sec-WebSocket-Key` 走升级，没有就走网页 |

## 和 Android App 的关系

两者共用同一套协议和同一个端口，可以同时连。2.0 起默认允许 4 台同时在用，车机设置页可调 1~8。

2.0 取消了 PIN 和设备配对：**连上 18765 就能控，不握手、不输码**。网页端和 App 都只是连上去即可（网页端仍会发一条 `pair` 拿车辆名字，车机直接回 ok）。谁连上了只体现在设置页的「同时在线」列表里，断开就消失，不落盘、不需要清理。

## 已知限制

- 没有 TLS，明文局域网，和 App 一样只适合车内可信网络。
- 网页不能后台播放通知、不能锁屏控制，就是一块遥控面板。
- 添加到主屏幕后是一个独立的窗口（`apple-mobile-web-app-capable`），没有地址栏，但本质仍是网页。
