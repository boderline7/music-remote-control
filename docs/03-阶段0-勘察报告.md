## 2. 播放器：怎么控制和监听

核心是 `app/.../player/PlayerHub.kt`，**一个 `object` 单例，进程内唯一**：

```
PlayerHub (object, 799 行)
├─ lateinit var player: ExoPlayer      // public getter，Application 里 init()
├─ current: StateFlow<Track?>          // 当前曲目（name / artistNames / album / durationMs）
├─ isPlaying / isBuffering: StateFlow<Boolean>
├─ queue: StateFlow<List<Pair<Int, Track>>>
├─ mode / sourceName / playMode / lyrics / status
└─ togglePlay() / next() / previous() / seekTo(ms) / jumpTo(index)
```

队列直接交给 ExoPlayer，所以通知栏、方向盘按键、车机媒体中心天然可用 —— 这一点很关键：**手机遥控和车机按键走的是同一个播放器、同一个队列，不会出现两套状态打架**。

`PlaybackService : MediaSessionService` 只在播放时提供系统媒体会话，不持有播放器（`onDestroy` 里有注释「播放器是进程级单例，这里只释放会话」）。

### 控制入口（全部可直接调用）

| 动作 | 现有入口 | 备注 |
|---|---|---|
| 播放 | `PlayerHub.togglePlay()` | 无独立 play()，内部按 `isPlaying` 分支 |
| 暂停 | `PlayerHub.togglePlay()` | 同上 |
| 上一首 | `PlayerHub.previous()` | 已设 `setMaxSeekToPreviousPositionMs(MAX)`，永远真切上一首 |
| 下一首 | `PlayerHub.next()` | 走 `manualNeighbor()`，与手机/方向盘行为一致 |
| 进度跳转 | `PlayerHub.seekTo(ms)` | 直接 `player.seekTo(ms)` |
| 音量 | **工程里完全没有** | `grep AudioManager` 0 命中 |

### 状态来源

| 需要 | 来源 | 可靠性 |
|---|---|---|
| 是否播放 | `PlayerHub.isPlaying` | 高 |
| 歌名 / 歌手 | `PlayerHub.current.value?.name / artistNames` | 高 |
| 专辑 | `current.value?.album?.name` | 高 |
| 进度 | `player.currentPosition` | 高（1 s 精度够用） |
| 总时长 | `Track.durationMs`，回退 `player.duration` | 高 |
| 音量 | 需新增 `AudioManager.STREAM_MUSIC` | 见下 |

**音量决策**：车机音量是系统音量（方向盘、车机旋钮调的都是 `STREAM_MUSIC`），播放器的 `player.volume` 只是 0..1 软件增益，改它会出现「车机显示 50% 但实际很轻」。所以 `setVolume` 走 `AudioManager.setStreamVolume`，`volumeMax` 取 `getStreamMaxVolume`，拿不到就不在 `state` 里带 `volume`（不填假值）。

## 3. 跑跑桌面依赖：必须摘掉

`CloudMusicApp.onCreate()` 第一行原本是：

```kotlin
check(ContainerGate.isPaopaoGuest(this)) { "CloudMusic must run inside Paopao Desktop" }
```

它校验调用栈里有 `top.niunaijun.blackbox.app.BActivityThread`、`/proc/self/maps` 里有宿主 APK。装到普通车机上会直接崩。**已删除**，这是独立 APK 的前提。同时 `app` 模块不再产出 `.ppmusic`（没有 Activity/Manifest，只有 DEX）—— 需求只做独立 APK，所以保持 `com.android.application` 不变。

## 4. 遥控服务挂哪里：不新增 Service

| 方案 | 判断 |
|---|---|
| 新建前台 Service | 不需要。会多一条常驻通知，且 Android 14+ 要求声明 `foregroundServiceType` |
| 依附 `PlaybackService` | 可行但耦合：遥控要在未播放时也能待命，而该 Service 播放完就 `stopSelf()` |
| **在 Application 里起独立线程**（采用） | 播放器是进程级单例，同进程直调零成本；进程活着遥控就在，进程被杀播放也没了 —— 语义一致 |

所以：`RemoteServer`（object）在 `CloudMusicApp.onCreate()` 里按持久化开关启动，内部一条 accept 线程 + 两条定时任务（1 s 推状态、5 s 看门狗）。**不新增任何 Service、不申请前台服务权限。**

风险留到阶段 4 实测：车机熄屏 / 长时间后台后，进程被系统回收会导致遥控和播放同时消失（这是一致的，不算缺陷）；若实测发现「播放还在、socket 被挂起」，再评估是否加前台服务。

## 5. 目标车机可能的限制

| 限制 | 影响 | 处理 |
|---|---|---|
| Android 9+ 默认禁明文 HTTP | **不影响**：WebSocket 是裸 TCP，不走 HTTP 明文策略 | 无需 `usesCleartextTraffic` |
| Android 12+ 后台启动限制 | 不影响已在前台的 App 内建 socket | — |
| Android 13+ 通知权限 | 仅影响媒体通知，不影响遥控 | 原工程已申请 |
| 车机多网卡（Wi-Fi + 4G） | 绑 `0.0.0.0` 即可，但 UI 显示的 IP 要挑对 | `localIpv4()` 取第一个 site-local IPv4；若车机同时有热点网段可能显示错，阶段 4 真机核对 |
| mDNS 组播被车机路由拦截 | 手机发现不到车机 | 手动 IP 兜底始终保留；`MulticastLock` **先不预设必需**，实测再决定 |

## 8. 1920×720 分析

`ui/theme/Theme.kt:92` 的自适应逻辑：

```kotlin
val (baseW, baseH) = if (landscape) 1280f to 720f else 800f to 1280f
val scale = min(widthPx / baseW, heightPx / baseH).coerceAtLeast(0.5f)
```

在 **1920×720** 上：`min(1920/1280, 720/720) = min(1.5, 1.0) = 1.0` → density = 1，设计稿的 720 dp 高度正好铺满，多出来的 **640 dp 全给宽度**。

这是正确的取舍：纵向不溢出，横向变宽。而且列表本来就是按宽度自适应的，不需要改：

- `HomeScreen.kt:151` 用 `maxWidth` 算列数 → 1920 下自动多排一列
- `BrowseScreens.kt:129` / `SearchScreen.kt:225` 用 `GridCells.Adaptive(200.dp)` → 同理

本次新增的遥控页按 1920 宽设计成**左右两栏**（左：开关 + 地址 + PIN，右：已配对设备），1280 宽下也不会挤。

唯一待定的：字体物理尺寸。1920×720 通常配 12.3" 屏，1 dp = 1 px 时 22 sp 正文约 2.4 mm，比手机小。**这个不能拍脑袋改** —— 全局放大字体会撑破现有布局。阶段 4 拿真机截图后再决定是否加一档全局缩放，现在的判断是先不动。
